# V9 — Transactional multiprocess replay store

Date: 2026-09-07

## Problem

The legacy JSONL replay store used an adjacent `O_EXCL` lock file. It failed closed under contention, but contention itself produced `store_busy_fail_closed` rather than a durable transactional decision, and stale lock files remained an operational gate. The next reliability requirement is a shared store in which concurrent processes racing on the same authorization deterministically produce one durable winner.

## Design

`sqlite-authorization-replay-store-v9.js` uses Node's built-in `node:sqlite` `DatabaseSync` and a file-backed SQLite database.

- `authorization_id` is the PRIMARY KEY.
- `BEGIN IMMEDIATE` acquires the write transaction before the reservation attempt.
- `INSERT ... ON CONFLICT DO NOTHING` atomically reserves the authorization ID.
- a successful insert is committed before `consume()` reports success.
- duplicate authorization IDs return `authorization_replay_detected`.
- database lock/busy conditions return `store_busy_fail_closed`.
- `journal_mode=WAL` and `synchronous=FULL` are enabled.
- metadata remains allowlisted through the existing sanitizer; authoritative ID/timestamp are generated by the store.

The existing `FileAuthorizationReplayStore` is retained for compatibility, but V9 is the preferred replay store for concurrent/multiprocess agent execution.

## Verification

`tests/sqlite-replay-v9.test.js` launches real independent Node processes against one database. It requires exactly one winner in a 16-process same-ID race, all 16 distinct IDs to commit, authoritative metadata protection, explicit busy fail-closed behavior, and invalid-ID rejection.

## Boundary

SQLite provides transactional single-host/multiprocess replay coordination. V9 does not claim distributed consensus across separate hosts or filesystems. A multi-host deployment still requires a transactional shared database/service with equivalent uniqueness and durability semantics.
